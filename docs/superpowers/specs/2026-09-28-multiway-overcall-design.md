# 멀티웨이: 플랫 뒤 오버콜 (3인 팟) 설계

작성 2026-09-28. 사용자 질문("멀티웨이 팟이 없네?")에서 나왔다. 스퀴즈 설계
(`2026-09-28-squeeze-after-flat-design.md`)의 후속이다.

## 왜 하는가

홀덤펍은 멀티웨이가 흔하다. 오픈 + 플랫 뒤의 BB는 가장 싸게 들어가는 자리라, 실전에서
가장 많이 나오는 판단 중 하나가 "BB에서 따라 들어가나"다. 지금 엔진은 플랫 뒤 자리에게
폴드와 스퀴즈 올인만 준다. 그래서 BB가 스퀴즈를 과하게 한다(BTN 오픈 + SB 플랫 뒤 27.7%,
2026-09-28) — 오버콜이라는 출구가 없으니 들어갈 핸드가 전부 스퀴즈로 몰린다.

## 무엇이 풀리고 무엇이 안 풀리는가

- **3인 플랍 전략은 풀 수 없다.** 쓰는 포스트플랍 솔버(b-inary postflop-solver)는 2인
  전용이다. 3인 보드를 치고 채점하는 것은 이 설계의 범위가 아니다.
- **3인 팟의 가치는 구할 수 있다.** 세 핸드의 쇼다운 승률은 몬테카를로로 센다. 여기에
  "포지션에 따라 승률을 얼마나 실현하는가"를 곱한다. 실현 비율은 이미 푼 2인 표에서
  잰다(같은 깊이, BTN 오픈-BB 콜 표: 플랍 몫 ÷ (승률 × 팟), 조합 가중).
- 그 가치로 프리플랍(오버콜 / 스퀴즈 / 폴드)을 푼다. 판단 연습의 핵심은 프리플랍이다.

## 게임

- 플랫 뒤 자리들의 선택지가 **폴드 / 콜(오버콜) / 스퀴즈 올인**. 오버콜 데이터
  (`vsFlatCall`)가 없으면 지금처럼 폴드 / 올인.
- 오버콜이 나오면 그 뒤 자리는 접는다(4인 이상은 다루지 않는다).
- 결과 `{ kind: "multiwayFlop"; opener; caller; overcaller }`. 판은 플랍 전에 끝나고
  (3벳 팟과 같은 방식), 두 상대의 카드를 까서 보여준 뒤 **세 핸드의 실제 3인 승률로 팟을
  나눠** 정산한다. 카드를 깔지 않으므로 운은 0.
- 투입액: 오버콜은 오픈액(+ BB면 앤티). 폴드는 낸 것 유지.

## 솔버 (`scripts/solve-preflop-3bet.ts`)

플랫한 자리 k, 그 뒤 m마다 오버콜 빈도 `oc[k][m]`. m의 첫 비폴드 액션이 판을 정한다:
콜이면 3인, 올인이면 스퀴즈.

- 생존 확률: `P(m까지 아무도 안 함) × (1 − 스퀴즈 − 오버콜)`.
- m의 오버콜 EV = `3인 몫(m) − 낸 것(m)`.
- 오프너 / k의 가치에 `첫 오버콜 확률 × (3인 몫 − 낸 것)` 항을 더한다.
- 3인 몫은 `scripts/data/multiway-<깊이>bb.json`의 표(아래). 없으면 오버콜을 풀지 않는다.

## 3인 몫 표 (`scripts/multiway-values.ts`)

- (오프너, 플랫한 자리, 오버콜한 자리) 조합마다 세 역할의 169개 클래스 몫(bb).
- 상대 레인지: 오프너 = 오픈, 플랫 = `vsOpenCall`, 오버콜 = `vsFlatCall`(없으면 씨앗:
  그 자리의 플랫 레인지).
- 승률: 상대 두 명의 조합을 레인지에서(카드 겹침 제외) 뽑고 보드 다섯 장을 뽑아 센다.
- 실현 비율: 플랍에서 마지막에 치는 자리는 IP 비율, 처음 치는 자리는 OOP 비율, 가운데는 둘의
  평균. 2인 표에서 잰 값을 쓰고 파일에 남긴다.
- 파이프라인 한 바퀴의 한 단계로 돌린다(플랍 표처럼 지난 레인지로 만들고 바퀴 평균).

## 성공 기준 (30bb)

1. BTN 오픈 + SB 플랫 뒤 BB 스퀴즈가 줄어든다(27.7% → 15% 이하)
2. BB의 오버콜이 의미 있게 쓰인다(BTN 오픈 + SB 플랫 뒤 10% 이상)
3. 플랍 도달률(2인 + 3벳 팟 + 3인 팟) 25~45%, 바퀴 사이 변화 < 1%p

## 순서

1. 엔진 + 가짜 데이터 테스트
2. 3인 몫 표 스크립트 + 테스트(대칭·합 확인)
3. 솔버에 오버콜
4. 파이프라인에 3인 몫 단계
5. 화면: 3인 팟 결과(두 상대 카드, 3인 승률 정산)
6. 30bb 파이프라인으로 기준 확인 — 켜는 것은 사용자 확인 뒤
